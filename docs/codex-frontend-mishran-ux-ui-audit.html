UX/UI Audit - Web, iOS, Android

Mishran has premium brand bones and native commerce depth, but the web cannot yet close an order.

The strongest product experience is split across platforms: the web is an editorial storefront with search, product detail pages, lead capture, WhatsApp fallback, schema, sitemap, and rich brand surfaces; the native apps carry true checkout, Razorpay, account, orders, push, and loyalty. For a premium Indian sweets ecommerce business, launch priority is to close the web commerce gap, convert gifting intent into configured products, deepen local/occasion discovery, and make retention measurable.

  • Overall readiness: 67/100 Sellable brand experience, incomplete transaction stack on web.
  • Top P0 Web checkout, account, and order tracking are explicit stubs.
  • Top P1 SEO/GEO is technically valid but thin for local, occasion, FAQ, review, and AI answer surfaces.
  • Top upside Existing gift-box, occasion, lead, product, and mobile checkout foundations make the next phase tractable.

Priority Findings

Annotated Findings with Severity, Impact, Effort

P0

Web checkout is not production ecommerce.

Category: Launch-Critical/Must Have. Impact: Very high. Effort: High.

The web route returns a commerce stub and WhatsApp fallback. Cart can collect intent, but paid acquisition, SEO traffic, and direct search traffic cannot complete purchase on the web. This is the largest revenue leak.

  • Port native checkout primitives: address picker, pincode/serviceability, slot picker for fresh tier, Razorpay create/verify, order confirmation.
  • Use the existing mobile API contract and server validation work before adding advanced merchandising.
  • Keep WhatsApp as assistive recovery, not the primary checkout path.

P0

Legal, help, and trust routes are linked but absent.

Category: Operational/Trust. Impact: High. Effort: Medium.

The footer includes shipping, returns, contact, about, careers, press, wholesale, privacy, terms, and accessibility links, while the actual app routes list does not include those pages. The footer also displays "FSSAI - pending". This undermines food-safety trust and can hurt conversion.

  • Ship legal/help pages before launch: privacy, terms, shipping, refunds, cancellation, accessibility, FSSAI license, contact.
  • Replace "FSSAI - pending" with the real license number or hide until ready.
  • Fix the 404 "Browse sweets" link, which points at `/sweets` while the real route is `/mithai`.

P1

SEO/GEO foundation exists, but answer-engine and local-intent coverage is thin.

Category: SEO/GEO & Discovery. Impact: High. Effort: Medium.

The code has sitemap, locale routes, Product schema, Organization schema, Breadcrumb schema, and honest price parsing. Missing pieces are the ones a premium Indian sweets business needs: LocalBusiness/service area, FAQ, reviews, delivery/return policy, occasion landing pages, city pages, festival pages, and internal links from stories into products.

  • Add LocalBusiness or FoodEstablishment schema with city/service-area truth.
  • Add FAQ schema for freshness, shelf life, delivery, gifting, bulk, allergens, Jain/sugar-free.
  • Use Occasions collection to create `/diwali-gifts`, `/wedding-mithai`, `/corporate-gifts`, `/rakhi-gifts`, city/local pages.

P1

Catalog discovery is functional, not commercial.

Category: Conversion & Revenue. Impact: High. Effort: Medium.

Search currently matches text fields and one tag select; sort is featured/A-Z/Z-A. Users shopping Indian sweets need task-oriented facets: occasion, freshness, delivery city, price band, dietary, shelf life, box compatibility, best sellers, giftable, festival, family, and availability.

  • Promote business facets already present in collections: family, freshnessStatus, dietaryTags, boxCompatibility, packagingCompatibility, leadTime.
  • Add merchandising lanes: "Same-day Delhi NCR", "Pan-India shelf-stable", "Sugar-free", "Wedding trays", "Corporate Diwali hampers".
  • Track search usage. The event type exists, but the catalog search input does not fire it.

Gift-box data exists, but the shopper experience is still a quote form.

Web Storefront

What Works and What Blocks Revenue

Strengths

  • Strong premium visual system: deep navy, product photography, restrained gold, editorial layouts.
  • Home page is not a generic grid: hero, vertical portals, and pillars give brand shape.
  • PDP has meaningful conversion affordances: pack sizes, quantity, delivery check, add to cart, buy now, WhatsApp, sticky mobile CTA.
  • Cart preserves draft intent and creates a useful WhatsApp message.
  • Lead flows exist for wedding, corporate, and gift-builder demand.

Risks

  • Checkout, account, and track-order are not real web flows.
  • Footer links expose non-existent routes and pending FSSAI status.
  • Discovery is catalog-first, not occasion/customer-job-first.
  • No social proof: verified reviews, customer photos, press, ratings, trust badges.
  • No web post-purchase loop: reorder, referrals, loyalty, recipient address book.

Mobile Apps

Native Apps Are Closer to Transaction-Ready

iOS

iOS has home, catalog, product detail, cart, checkout, address creation, pincode serviceability, slots, Razorpay, order confirmation handoff, order detail, account, Apple Wallet loyalty pass, push and Live Activity foundations.

  • Good: checkout flow is clear and stateful.
  • Good: iOS accessibility audit covers labels, 44pt tap targets, and Dynamic Type checks.
  • Gap: some checkout messages are hardcoded English; physical-device VoiceOver and reduced-motion signoff is pending.
  • Gap: merchandising/gifting depth lags the web lead surfaces.

Android

Android has home, vertical catalog tabs, search/filter, product detail, cart, checkout, Razorpay launch/verify, order flows, account, push, and widgets.

  • Good: checkout copy changes according to blocked state: select address, checking, pick slot, place order.
  • Good: catalog has vertical segmentation and pull-to-refresh.
  • Gap: Android home has an explicit i18n TODO for hardcoded English labels.
  • Gap: Google Wallet loyalty parity is not present.

Frontend Design Skill Audit

What the Newly Installed `frontend-design` Skill Adds

Skill verdict: Mishran does not need a broad visual redesign before launch. It needs the existing premium editorial system carried through the missing revenue, trust, and retention flows.

Intent and Aesthetic Fit

The skill first asks whether the interface has a clear audience and aesthetic. Mishran does: premium Indian sweets ecommerce, using a dark editorial storefront system rather than a generic white ecommerce grid.

  • Status: Strong.
  • Evidence: `DESIGN.md` defines Malgudi Blue v2 with navy canvas, blue surfaces, restrained gold, product photography, and editorial hierarchy.
  • Risk: Brand strength fades on stub pages because checkout/account/track-order use a generic "coming soon" pattern.

Tokens and Visual System

The skill checks whether colors, spacing, radius, typography, and shadows are intentional. Mishran has a real token system across `DESIGN.md`, CSS variables, and theme config.

  • Status: Good.
  • Evidence: `app/globals.css`, `lib/themes.ts`, `DESIGN.md`.
  • Risk: Some legacy/theme variants and decorative grid/orb styles can dilute the cleaner Malgudi Blue direction if overused.

Layout and Hierarchy

The skill favors semantic layout, CSS Grid for major structure, strong hierarchy, and asymmetric/product-specific composition. Mishran's home, vertical hubs, and PDP mostly pass.

  • Status: Good on discovery/PDP, weak on commerce stubs.
  • Evidence: `BrandHero`, `VerticalPortals`, `VerticalHub`, `MithaiPDP`.
  • Risk: Catalog cards are visually polished but commercially under-faceted.

  • Promote the Malgudi Blue tokens into every missing commerce surface before introducing new styles.

Prioritized Roadmap

Phased Plan

Phase 1 - Launch-Critical Trust and Web Commerce

  • Build web checkout and payment by reusing the mobile API contract.
  • Ship account, addresses, order tracking, and order confirmation on web.
  • Publish legal/help pages and replace pending FSSAI language.
  • Fix dead footer routes and `/sweets` 404 CTA.

Phase 2 - Conversion and Merchandising

  • Add advanced catalog facets and business-led product lanes.
  • Add PDP trust blocks, cross-sells, reviews placeholder model, and delivery clarity.
  • Replace `buyNow -> cart` with `buyNow -> checkout` after checkout exists.
  • Add cart upsells and gift packaging prompts.

Phase 3 - Gifting, Wedding, Corporate Revenue

  • Turn GiftBoxes and Occasions into shoppable pages.
  • Build a visual gift-box configurator.
  • Add wedding and corporate package proof: pricing anchors, photos, SLAs, testimonials.
  • Enable saved recipient lists and quote-to-order conversion tracking.

Phase 4 - SEO/GEO and Content Scale

  • Create festival, city, delivery-tier, dietary, and occasion landing pages.
  • Add LocalBusiness, FAQ, OfferShippingDetails, return policy, and review schema where honest.
  • Complete native-quality localization for chosen launch languages.
  • Build internal linking from stories to products, gift boxes, karigars, and occasions.

Phase 5 - Retention, Loyalty, and Lifecycle

  • Web loyalty hub, Android Google Wallet parity, Apple Wallet pass polish.
  • Review capture, reorder, festival reminders, referrals, and post-purchase education.
  • Lifecycle campaigns through email/SMS/push after consent.
  • Analytics dashboard and event taxonomy cleanup.
