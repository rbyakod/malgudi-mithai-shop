1. The mental model

Vercel listens to the main branch of this Git repo. Every push to main triggers a fresh production build. Every push to any other branch triggers a preview build at a temporary URL. There is no separate "deploy" command in the normal flow — you just push.

Production URL: https://mishran.shop (or whichever canonical domain is wired in Vercel).
Preview URL: https://mishran-git-<branch>-<org>.vercel.app (Vercel generates this on each push).

One-line summary: git push origin main → Vercel builds → live in ~2 minutes.

2. Daily cycle (the 90-second version)

1 Pull latest

git switch main
git pull --rebase origin main

Rebases your local commits on top of latest remote. Avoids merge bubbles.

2 Branch for the work

git switch -c fix/whatever-the-thing-is

Branch name format: <kind>/<short-slug>. Kinds: fix, feat, chore, docs, test, refactor.

3 Make changes, commit small

Test locally before each commit:

npm run lint && npx tsc --noEmit && npm run test:unit

Then commit — one logical change per commit:

git add <specific-files>
git commit -m "fix: short imperative subject"

Commit message convention (Conventional Commits):

  • feat: new user-facing capability
  • fix: bug fix
  • chore: deps, config, build
  • docs: docs only
  • test: test-only change
  • refactor: no behavior change

4 Push the branch

git push -u origin fix/whatever-the-thing-is

Vercel immediately starts a preview build. The URL lands in the GitHub PR and the Vercel dashboard.

5 Open a PR

gh pr create --title "fix: short subject" --body "..."

CI runs (lint, tsc, unit, build, e2e). Preview URL is visible in the PR.

6 Merge

Squash-merge via GitHub UI. Vercel builds main → production live in ~2 minutes.

3. First time on a new Mac

  1. Install Node 22: brew install node@22 or use nvm install 22.
  2. Install MongoDB for local dev: brew tap mongodb/brew && brew install mongodb-community, then brew services start mongodb-community.
  3. Clone the repo: git clone <repo-url>.
  4. Install deps: npm install.
  5. Copy .env.example to .env.local and fill in dev values (Mongo URI mongodb://127.0.0.1:27017/mishran-dev, random strings for secrets).
  6. Seed: npm run seed.
  7. Run: npm run dev → open http://localhost:3000.
  8. (Optional) Install Vercel CLI: npm i -g vercel — useful for vercel logs and vercel env pull.

4. Working on a feature branch

Branches are cheap. Use them even for one-line fixes — the preview URL is worth it.

git switch main
git pull --rebase
git switch -c feat/snacks-search
# edit, lint, test
git commit -m "feat(snacks): add product name search"
git push -u origin feat/snacks-search

5. Preview deploys (auto-magic)

Every push to a non-main branch produces a fresh preview URL. Share it with the team for review.

  • Find it in the GitHub PR (Vercel bot comments automatically), or in the Vercel dashboard.
  • Preview uses the same env vars as Production (set in Vercel → Settings → Environment Variables → check both "Production" and "Preview").
  • Preview connects to the same MongoDB cluster by default. If you need an isolated preview DB, set a different MONGODB_URI scoped to Preview only.
Gotcha: set NODE_ENV=production on Preview env vars so Payload admin doesn't auto-login. The auto-login gate checks NODE_ENV, VERCEL_ENV, and CI.

6. Merging to main = production

  1. Wait for CI to be green on the PR.
  2. Squash-merge via GitHub UI (or gh pr merge --squash).
  3. Vercel builds main. Watch in dashboard or vercel logs <url>.
  4. Production is live when the build goes green (~2 min for clean changes; up to 5 min if cold).

7. Rolling back a bad deploy

Two paths depending on severity:

Path A: Vercel dashboard (instant, no code change)

  1. Vercel → Project → Deployments.
  2. Find the last known-good deployment.
  3. Click the ⋯ menu → "Promote to Production".
  4. Currents traffic routes to the old build instantly.

Path B: Git revert (the proper fix)

git switch main
git pull
git revert <bad-commit-sha>
git push

This creates a new commit that undoes the bad one. Vercel builds the fixed state.

8. When env vars change

  1. Vercel dashboard → Settings → Environment Variables.
  2. Add or edit the variable. Pick the right scope (Production / Preview / Development).
  3. Save. No redeploy happens automatically — env vars are baked at build time.
  4. Trigger a redeploy: push any commit to main, OR Vercel → Deployments → "Redeploy".

9. Database schema changes (Payload migrations)

Payload 3.x with MongoDB is schema-on-read. Adding a field to a collection config does not require a migration script — the next time Payload boots, it sees the new field and accepts writes. Existing docs simply don't have the field until updated.

Important: if you remove or rename a field, existing documents keep the old field. Plan a backfill explicitly. Payload does not auto-delete fields.

10. Discipline that keeps us sane

  • Never push to main without a PR. Even as the sole dev, the CI gate catches lockfile drift and type errors cheaply.
  • Always run npm run lint && npx tsc --noEmit before pushing.
  • Always commit package-lock.json alongside package.json changes.
  • One logical change per commit. Mixed-purpose commits make rollback hell.
  • Branch name describes the change; commit subject describes the action.
  • Don't bypass hooks with --no-verify. If a hook fails, fix the cause.
  • Squash-merge from PR — keeps main history linear and readable.
